# 工具循环控制与飞书 Base 命令修复需求

## 目标

修复长任务中工具调用次数过早耗尽、达到上限后假装完成、以及飞书 Base CLI 常用参数被模型误猜导致反复失败的问题。

## 用户故事

- 作为用户，我要求 Agent 创建多维表格这类多步骤任务时，不能因为 10 次工具调用就静默停止。
- 作为用户，我希望 Agent 如果确实无法继续，应明确说明未完成原因，而不是回复“已处理完成”。
- 作为 Agent，我需要在调用飞书 CLI 前获得足够明确的 Base 命令规则，减少用错误 flag 反复试错。
- 作为维护者，我需要有离线测试覆盖工具轮次上限、重复工具调用保护和 Base 命令校验。

## 接受标准

- 默认工具轮次预算高于 10，且可以通过环境变量调整。
- 达到工具轮次上限时，流事件必须包含明确错误，飞书回复不得落到“好的，已处理完成”。
- 对重复调用完全相同工具和参数的行为进行限流，避免无限循环或重复写操作。
- `LarkCliTool` 对已知 Base 命令误用直接返回可修复错误，包括 `base +create`、`--title`、`--format`、`--base` 等。
- README 记录新的工具预算配置和 Base CLI 常用命令。

## 非目标

- 不新增专用 BaseTool，继续保持通用 `LarkCli` 工具。
- 不保证外部飞书接口一定成功；真实成功仍取决于 CLI 登录态、应用权限、飞书接口和网络。
- 不实现跨用户、跨资源的分布式锁；本次只处理单轮 Agent 工具循环。

## 环境与兼容性

- Node.js >= 18。
- 测试不依赖真实飞书凭证或真实 LLM。
- 继续兼容现有 `QueryEngine` 构造参数。
